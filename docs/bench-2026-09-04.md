## 2. Step 2 — file format vs `tests/golden/`: PASS

MEASURED, comparing against `tests/golden/20250715_P3HT9505_KPF6/`:

- Spectra files: 8 columns, headers identical to golden —
  `Wavelength (nm) / Absorbance / Column 3 (a. u.) / Column 4 (a. u.) / Measured value (a.u.) /
  Spectrum number / Time (s) / Corrected time (s)`.
- `CVspectra.txt` column 6 is **`Index`**, not `Spectrum number` — this is CORRECT; the golden CV
  file has `Index` too. Do not "fix" it.
- Dark and reference (columns 3 and 4) are populated for spectrum 0 only and blank thereafter:
  1265 populated rows out of 26565 in `spectra(0).txt`, exactly one spectrum's worth. Matches the
  spec and the golden file's pattern.
- One NaN in `Time (s)` per spectrum block, in ours and in golden alike — same structural
  signature, scaled by spectrum count.
- Echem files: `steps(N).txt` = 5 columns
  (`Time (s) / Corrected time (s) / WE(1).Potential (V) / WE(1).Current (A) / Index`),
  `CV.txt` = 2 columns (`WE(1).Potential (V) / WE(1).Current (A)`).

**Absorbance values are meaningless in this run and that is expected** — the shutter was closed, so
dark ≈ reference ≈ sample ≈ 420 counts and the ratio is noise (8982 NaN + 513 inf of 26565 rows in
`spectra(0).txt`). The headless script cannot stage a shutter change between dark and reference, so
it can never produce meaningful optics. **Do not try to validate optics headlessly — that is the
GUI's job**, via the separate Collect New buttons for dark and reference on the Instrument tab.

## 3. The cadence defect — a file that looked normal and was not

MEASURED — the CV segment requested a spectrum every **10 ms** and achieved **29.9 ms**. It
collected 481 spectra spanning **14.301 s**, while the CV itself (2.4 V at 500 mV/s) lasts **4.8 s**.
So roughly two thirds of `CVspectra.txt` recorded a cell that had already stopped — in a file whose
shape, headers and point count all look perfectly normal.

MEASURED — the chrono segments were fine: 250.4 ms achieved against 250 ms requested.

MEASURED — **`_warn_if_cadence_unachievable()` did not fire**, because it compared
`integration × scan_averages` (2.6439 × 1 = 2.6 ms) against the 10 ms step and ignored everything
else. Per-spectrum cost, measured free-running at 2.6439 ms integration:

| averages | integration × averages | measured | overhead |
|---|---|---|---|
| 1 | 2.6 ms | 8.5 ms | 5.9 ms |
| 5 | 13.2 ms | 23.1 ms | 9.9 ms |
| 10 | 26.4 ms | 36.2 ms | 9.7 ms |
| 20 | 52.9 ms | 62.9 ms | 10.0 ms |
| 50 | 132.2 ms | 142.7 ms | 10.5 ms |

The overhead is **flat ~10 ms**, not proportional — it is the USB round trip per spectrum. In-run it
is worse (29.9 ms observed at 1 average), because `on_tick` pumps the potentiostat every spectrum,
which is itself an instrument call. INFERRED: ~20 ms of the in-run cost is that pump; not isolated.

**Consequence for settings:** the real budget is `integration × averages + ~30 ms`. At this rig's
2.6439 ms integration, a 100 ms CV step holds **26 averages**, not the ~37 the naive arithmetic
implies. `scan_averages = 20` fits with 17 ms to spare; `scan_averages = 10` is the comfortable
choice.

## 4. Spectrometer wavelength range — the >1100 nm question

MEASURED, read from the device's own calibration (`AVS_GetLambda`, serial 1404154U1):

| | |
|---|---|
| real detector pixels | **2048** (the SDK returns a 4096-slot array; the tail is zero padding — do not read `array[-1]`) |
| calibrated range reported | **174.54 – 1326.60 nm** |
| dispersion | 0.5628 nm/pixel |
| `measconfig` pixels | start 0, stop 2047 |

MEASURED — spec-echem's hardcoded slice (`CAL_START_PX = 395`, `CAL_STOP_PX = 1659`) delivers
**410.20 – 1123.72 nm**, 1265 pixels. It discards 395 pixels at the blue end (174.54–409.61 nm) and
**388 pixels at the red end (1124.25–1326.60 nm)**. 1100 nm is inside the slice (pixel 1615);
1150 nm (pixel 1709) and 1200 nm (pixel 1803) are outside it but within the detector's calibration.

### The red end — MEASURED, lamp on, and it settles the question

Taken with the shutter open, 1.1 ms x 20 averages, reading raw counts across all 2048 pixels.
Peak **24127 counts at 655.5 nm** (37% of the 65535 full scale). The reference number is the
**blue-end floor: 721 counts** over pixels 0-200, which sit below the optics cutoff where no light
can physically arrive — that is the detector's baseline, not a signal.

| nm | counts | above floor | % of peak |
|---|---|---|---|
| 1000.0 | 1841 | 1120 | 7.6% |
| 1050.0 | 1002 | 281 | 4.2% |
| 1100.2 | 787 | **66** | 3.3% |
| 1123.7 (current red edge) | 738 | **17** | 3.1% |
| 1150.4 | 721 | **0** | 3.0% |
| 1200-1326 | ~1046 median | — | — |

**Silicon is finished by ~1050 nm on this rig.** At 1100 nm there are 66 counts of signal on a
721-count pedestal; at the current edge, 17; past 1150 nm the array reads exactly its floor. The
apparent rise beyond 1200 nm is INFERRED to be array-edge / dark structure rather than light: a dead
zone followed by a step up is not a spectrum, and a real signal would continue smoothly instead of
resurrecting.

**This inverts the premise.** The open item was recorded as "a user on the ULS2048L rig needs
>1100 nm", but the current 1123.72 nm edge already extends past where this rig has usable signal —
widening the slice would add 388 pixels of baseline. The honest usable window here is about
**400-1000 nm** (400.2 nm gives 1608 counts, 887 above floor). If OMIEC polaron bands beyond
~1100 nm matter scientifically, no configuration change reaches them: that is an InGaAs detector,
not a code fix.

The wavelength-window redesign is still worth doing on its own merits (below) — it just is not a
route to the NIR on this hardware.

### Outcome: no change (Dean, 2026-09-04) — "no changes are needed based on real data"

The rework below is **not being built.** The measurement above removed its reason: this rig's
window already covers everything the detector can see. The design is recorded only so that a future
InGaAs spectrometer does not have to re-derive it.

### The design, if a detector ever makes it worth building

Three concepts that today's code conflates, to be separated: (1) **hard limits** discovered per
spectrometer from the device at connect, never hardcoded; (2) a **default window in nm**, not
pixels; (3) an **operator window** anywhere inside the hard limits. On the default Dean chose
**the best part of that spectrometer's range over consistency between instruments** — a changed row
count on the PLU rig is acceptable and is not a reason to keep the old slice. (The alternative,
pinning PLU's historical 1265 rows, was recommended and overruled; recorded as his call.)

MEASURED — the optics are real this time: **absorbance is 100% finite** (0 NaN, 0 inf across 304865

MEASURED — echem: `CV.txt` 240 points, −0.503 to +0.704 V, peak 71.0 µA (9.90 kΩ);
`steps(0).txt` 300 points held at +0.100 V drawing 10.1 µA (9.91 kΩ).

MEASURED — **cadence is fine.** The run log's `mean 127.4 ms (target 100.0)` is skewed by one
interval; the steady-state median is **100.5 ms**. The pacing works, and 1.1 ms x 20 + 30 ms
overhead = 52 ms fits the 100 ms step with room, exactly as the new advisory predicts.

MEASURED — **the trigger was off.** The metadata and the saved settings file both record
`trigger: false`, and every segment logged `trigger=False`. Consequence: spectrum 0 free-ran at
t=0 while the Autolab does not start its waveform until `autolab_pulse_delay_s` = 5.95 s later —
which is the 6.1-6.3 s first interval visible in every segment. **Spectrum 0 records the cell before
the experiment starts**; spectra 1 onward are correctly time-locked. The run's only defect, and it
is a settings state, not code: `bench.ini` says `trigger = True` and it resolves to True in code.

INFERRED cause, and fixed today: the checkbox read **"Wait for Gamry trigger"** even in Autolab
mode, which is easy to read as "not my instrument". It is not Gamry-specific — it arms the
spectrometer to wait for a hardware edge whichever potentiostat raises it. Relabelled **"Wait for
hardware trigger"** with a tooltip naming both DIGOUT0 and P1.A and saying what happens when it is
off. Verified to come up checked from `bench.ini`.

**Careful on the re-run:** the saved settings file `20260904_settings_test_001.json` carries
`trigger: false`. Loading it re-applies that; tick the box after loading, or re-save it.

## 5. Defects found and fixed today

- **`examples/bench_autolab_fullrun.py` set `doping_potential_final`, which is not a settings key.**
  The real key is `doping_potential_end`. Silently ignored, so the "shortened" run used the 0.8 V
  default and ran **11 doping/dedoping cycles up to +0.80 V instead of 1** — 24 segments rather than
  4, and why the run took as long as it did. Found independently here and on the Mac side within
  the same hour; the fix that landed is `f1c78ac`, verified back to 4 segments (~52 s). This is the
  settings layer's sharpest edge: **an unknown settings key is not an error** — it writes cleanly,
  reads back cleanly, and changes nothing. Nothing in the pipeline catches that today.
- **`_warn_if_cadence_unachievable()` ignored per-spectrum overhead** (section 3). Now counts a
  named `SPECTRUM_OVERHEAD_S = 0.030`, and suggests a scan-averages count that would fit. Warning
  only — no timing, pacing or data behaviour changed.

## 7. Tried and did not work

- **Validating optics headlessly.** `bench_autolab_fullrun.py` takes its dark and reference back to
  back with no chance to move the shutter, so absorbance is structurally valid and numerically
  meaningless. Not a bug in the script — a limit of headless. Use the GUI.
- **`strings` for reading `.nox` files.** Not present in this Git Bash. A regex over the bytes works
  fine: a `.nox` is .NET binary serialization and its type/label strings extract cleanly, no NOVA
  and no instrument needed. That is how the DIO evidence in `autolab-driver-finishing.md` was read.
- **Reading `wavelengths()[-1]` to get the red limit.** The SDK hands back 4096 slots for a
  2048-pixel detector and zero-pads the rest, so the naive last element is `0.00 nm` and the array
  is not monotonic. Take the increasing prefix.
