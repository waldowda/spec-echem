## 1. What the `.nox` route costs, and why no parameter fixes it

`Measure()` hands control to a procedure, which walks its command list before the
recorder ever runs:

```
[1] FHGetSetValues            Mode, Bandwidth, CurrentRange
[2] FHSetSetpointPotential    the segment's potential
[3] FHSwitchCell              ON
[4] FHWait                    (was 5.0 s; set to 0)
[5] FHLevel                   recording starts here
```

- MEASURED: `CalcTime[0]` ≈ **0.93 s** for CA, **1.16 s** for CV, with `FHWait = 0`.
- MEASURED: the 0.23 s CV costs above CA is its **one extra command**,
  `FHPreCurrentRangingCV`. So the startup is a **sum of per-command overheads**, and
  deleting commands is the only thing that shortens it.
- MEASURED: `UseFastOptions = True` on `FHLevel` changed `CalcTime[0]` by nothing
  (0.924 → 0.920 s, inside the CV control's own run-to-run scatter). It did suppress
  the settled ADC dither (`sd 3.8e-10` → exactly 0, 295 bit-identical samples), which
  is an unexplained side effect with no measured benefit, so it was reverted.

**The stock 5 s `FHWait` was not settling at rest.** The driver writes the segment's
potential into `[2]`, which runs *before* the wait — so the cell sat at the doping
potential for 5 s with nothing recording. `autolab_wait_s` now writes `FHWait`;
`bench.ini` sets it to 0.

## 2. `Ei` mode — Python drives the chrono hold

No `LoadProcedure` for doping / dedoping / pre-dedoping. Mode, CurrentRange and
Setpoint are written while the cell is still **open**, off the clock; then cell ON,
edge, sample. CV keeps the procedure.

The pulse delay is **0** in this mode. There is no procedure startup left to predict,
which also removes the ±35 ms floor the fixed-delay approach could never beat —
`CalcTime[0]` itself scattered over 0.904–0.976 s, so a single predicted number could
never do better than that.

MEASURED on the dummy (`20260909_test12`):

```
prededoping  0.0001 V   -1.28e-07 A
steps(0)     0.0999 V   +9.94e-06 A   ->  10.05 kΩ
steps(1)     0.1999 V   +2.00e-05 A   ->   9.98 kΩ
```

Select with `autolab_ca_mode = ei`; `procedure` restores the old path and nothing
else changes.

## 3. The latch — `Ei.Current` is not a live property

**This is the one to remember.** `Ei.Current`, `Ei.Potential` and the overload flags
hold whatever `Ei.Sampler.Sample()` last loaded.

`20260909_test11` recorded `0.000125 V` and `-4.18 nA` for **every sample of every
segment**, identical across holds at 0.0, 0.1 and 0.2 V, because nothing sampled —
the reads returned the connect-time latch forever.

MEASURED, `examples/probe_ei_live_report.txt`, 10 kΩ dummy:

| strategy | at 0.1 V | at 0.2 V |
|---|---|---|
| `Ei.Current` bare | 9.9304e-06 (ok) | **9.9304e-06 — the 0.1 V value** |
| `Sampler.Sample()` then `Ei.Current` | 9.9304e-06 | **2.0035e-05** (0.2% off) |
| `Instrument.GetSignal()` | same | same |
| `Instrument.CreateSampler()` | not available on this instrument | |

`Sample()` is preferred over `Instrument.GetSignal()` — equally live, but one call
refreshes **all** signals, so potential and current come from the same instant rather
than possibly straddling two samples.

**This was never confined to `Ei` mode.** `pump()` reads the overload flags off that
same latch every spectrum in *both* modes, so the check that exists to stop a
meaningless segment being written as ordinary had **never been able to fire**.

`fakes._FakeEi` now models the latch — `true_potential`/`true_current` (what the cell
is doing) separate from `Potential`/`Current` (what a read returns). With live
properties in the fake, a driver that never samples passes every test and then writes
300 identical rows on the rig, which is exactly what happened.

## 4. The ~110 nA startup artifact — solved, and it was `FHLevel`

Every chrono segment through test7 had its **first five samples** ~110 nA low, then
went flat. MEASURED discriminator: at `chrono_delta_time = 0.05 s` it still covered
**five samples (0.25 s)**, not 0.5 s — so it was **sample-based**, a recorder
artifact, not analogue settling.

In `Ei` mode it is **gone**: first5 − settled = `+7.9, +3.7, −1.8 nA`, inside the
noise. It belonged to `FHLevel` arming, which could only be established by removing
`FHLevel`.

## 5. Everything else measured today

- **Trigger pin**: bit `0x01` = **pin 1 of `DioPortsP1[0]` (Port_A)**. All seven other
  bits gave no scan with the closing `0xFF` control still firing (`probe_dio_pin.py`).
  `autolab_dio_mask = 1`. The AvaLight shutter is **not** on that port — an all-pins
  pulse produced no audible shutter movement.
- **DIO layout**: five ports per connector on each of P1 and P2. `Port_C_Upper` and
  `Port_C_Lower` are the **nibbles of `Port_C`**, so a different index is not always an
  independent line. Independent pairs: A/B/C within a connector, or across P1/P2.
- **Parameter keys**: CV staircase `IdNames` match the bench-measured indices exactly,
  all seven. The SDK manual's 8-parameter list does **not** describe this command.
  Chrono keys read off the rig: `Duration`, `Interval time in µs` (**MICRO SIGN
  U+00B5**, not Greek mu), `Setpoint value`, `Time`.
- **`Interval time in µs` is mislabelled by the vendor** — the display name says
  `(s)`, the template ships `0.01`, and the data agrees with seconds. Do not "fix" it
  into a 10⁶ scaling bug.
- **Abort works on hardware** (`20260909_test4`): cell off, procedure stopped, no
  partial files, completed segments intact.
- **The Avantes genuinely waits for the edge**: `EDGE -> spectrum 0` = **+30–34 ms**
  across every segment of every run, ≈ integration (1.1 ms × 20) + overhead. Free-run
  would be ~0 or negative.

## 6. Defects found — all invisible in files that looked normal

1. **`load_settings` backfilled from `DEFAULT_SETTINGS`**, not from bench defaults, so
   loading any settings file silently reverted every `bench.ini` value the file didn't
   mention. `20260909_test5` ran with `autolab_wait_s=None` and `autolab_dio_mask=255`
   while `bench.ini` said `0.0` and `1`. Now overlays on `MainWindow.bench_base()`.
2. **`_neutralise_extra_ca_steps` zeroed the extra `FHLevel` durations but not the
   setpoint commands beside them** — so the stock template still drove the cell to
   **+0.5 V and −0.5 V** after every chrono segment, writing nothing because the
   recorders were zero-length. Harmless on a resistor. Now parked at the segment's own
   potential.
3. **The pulse deadline was anchored at `_pulse_trigger` entry**, adding `Measure()`'s
   own 0.128–0.287 s. The edge was landing ~0.21 s *after* the recorder's first sample
   on every chrono segment. Anchored on cell ON: residual 28–32 ms.
4. **The overload check could never fire** (§3).
5. **`Ei.Setpoint` verified at `1e-9`** — correct for procedure parameters (software
   values that round-trip exactly), wrong for a hardware DAC, which snaps. Killed
   `test10` at the first non-zero potential (0.1 V applied as 0.099945, 55 µV away).
   `AUTOLAB_SETPOINT_TOL_V = 2 mV`.

## 7. Noise — the `Ei` trade, and why it doesn't matter here

`Ei` sampling gives `sd` **3.4–7.3 nA** against the recorder's ~0–2.2 nA. `FHLevel` is
the instrument's own buffer and evidently filters; `Ei` reads are instantaneous.

**Dean, 2026-09-09: OMIEC currents run mA to µA, so single-digit nA of scatter is
fine.** This closes the concern — it is not a reason to prefer the procedure path. If
a future sample ever does need it, the fix is averaging several reads per point.
